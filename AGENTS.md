# RayoMD GUI Agent Guide

Read this file before changing the project.

## Product Goal

RayoMD GUI is the desktop app of RayoMD: write Markdown, see the PDF the engine makes as you
type, export it. It looks and feels like Omarchy's own apps (Omawrite, Hype) and follows the
current Omarchy theme live, on Omarchy first, then on any Linux with Wayland and on Windows.

It runs on its own toolkit: a software renderer, a font rasterizer, widgets and a text editor
of its own over thin platform layers, Wayland on Linux and Win32 on Windows. No Qt, no GTK, no
ImGui, no SDL. On Linux the executable needs `libc.so.6` only: the Wayland wire protocol, the
XKB keymap reader, the Compose reader and the D-Bus client are ours. The one library loaded at
run time is glibc's `libm.so.6`, which the engine loads when an SVG image needs a
transcendental function, as the `rayomd` CLI does. On Windows it needs system DLLs only.

The preview is drawn by our own PDF rasterizer from the PDF bytes the engine just built in
memory, so it is the PDF, not an approximation of it.

## Repository Layout

- `external/rayomd` — the engine, a git submodule of
  [Butterski/rayomd](https://github.com/Butterski/rayomd), built through its `rayomd::engine`
  library. Engine changes are made in `rayomd`, then the submodule moves to that commit;
  never edit `external/rayomd` here.
- `src/gfx/` — pixels: geometry, paths and flattening, the exact-area rasterizer, the
  stroker, the canvas (fills, gradients, images, masks, clips), the pixel kernels (C++
  reference and x86-64 assembly in `src/gfx/x86_64/`), the PNG writer and CRC-32, icon path
  parsing.
- `src/text/` — fonts: sfnt and collections, TrueType and CFF outlines, the system font index,
  the interface font choice (Omarchy's `monospace`), the glyph cache, text runs and cell widths
  (`unicode_tables.inc`, generated by `scripts/generate_unicode_tables.py`).
- `src/pdf/` — the preview renderer: the PDF object reader, the content stream interpreter, PDF
  fonts, images and the JPEG decoder.
- `src/ui/` — the toolkit: the Omarchy theme resolver and bundled themes
  (`omarchy_themes.inc`, generated by `scripts/import_omarchy_themes.py`), UI tokens, icons, the
  immediate-mode core, the display list and tile compositor, widgets, the text editor, the
  settings file.
- `src/app/` — the app, independent of the platform: the `Platform` interface, export settings,
  the document, the build worker, preview pages, the main window, arguments and snapshot mode.
- `src/platform/linux/` — Wayland, keyboard (XKB keymap, keysyms, Compose), D-Bus and the
  desktop portal, Omarchy and Hyprland integration, the event loop; all of it is the library
  `rayomd_gui_linux`, which the tests link too. `main_linux.cpp` is the executable
  `rayomd-gui`: the startup sequence of `src/app/app.h`, with the portal, the Omarchy watcher
  and Hyprland's rounding wired into the event loop.
- `src/platform/win32/` — the Win32 window, input, shell integration, delay-loaded system DLLs,
  resources, `main_win32.cpp`.
- `tests/` — `rayomd-gui-tests` (one executable, `RGUI_TEST("module.name")`; arguments select
  tests by name prefix), its data and corpus.
- `tests/e2e/` — the end-to-end runs: `run_compositor.sh weston|sway <rayomd-gui> <out dir>`
  starts a headless compositor in a temporary HOME and private `XDG_RUNTIME_DIR`, with an
  Omarchy theme made from `test-theme.toml`, takes `rayomd-gui --snapshot` of
  `external/rayomd/tester.md` and checks it with `check_snapshot.py`; `sway.conf` sizes sway's
  headless output. The ctest entries `rayomd-gui-wayland-weston` (client-side decorations) and
  `rayomd-gui-wayland-sway` (server-side) leave `e2e/<compositor>/out.png` in the build
  directory.
- `tests/fuzz/` — libFuzzer harnesses, one per reader of outside data (PDF, JPEG, fonts, theme
  TOML and tokens, fontconfig XML, settings, XKB keymaps, Compose, D-Bus, Wayland wire), the seed
  generator `rgui-fuzz-seeds`, `run_fuzzers.sh`, and `regressions/<harness>/`: minimized inputs
  that once crashed, replayed by the unit test `fuzz.regressions` in every build.
- `linux/` — the desktop file, icons and the Arch PKGBUILD.
- `assets/` — the app icon (`rayomd.ico`, `rayomd.png`) and the README's screenshots
  (`screenshot-*.png`). The README's sizes, timings and screenshots follow the app: update them
  with a change that makes them wrong, with the date of the measurement.
- `third_party/omarchy/` — the MIT notices of the Omarchy, Omawrite and Hype material and what
  came from where.

## Conventions

- Languages: C++17 by default. C11 for the Linux OS-protocol code (event loop, Wayland wire,
  D-Bus wire, Hyprland IPC) and the CRC-32 table. x86-64 GNU assembly (`.S`, through the C
  preprocessor) for the pixel and JPEG kernels; every assembly kernel has a C++ scalar
  reference, and the two must agree bit for bit.
- Toolchain: GCC or Clang only (MinGW-w64 UCRT64 on Windows), x86-64 only, CMake 3.21 or newer.
- No libm calls: rounding, floor, ceil and sqrt go through `RayoMd::ExactMath`
  (`external/rayomd/src/common/exact_math.h`). Nothing needs trigonometry: icons have no arcs,
  round joins and caps use a constant unit-circle table, rounded corners the Bézier constant
  0.5522847498.
- Our code throws no exceptions. No iostreams: C stdio, `RayoMd::File` and platform APIs.
- Every reader of outside data checks its bounds and fails closed: fonts, PDFs, JPEG, keymaps,
  Compose files, TOML, XML, D-Bus, Wayland.
- Work per input stays bounded so no document can stall the app. The preview renderer spends
  every page from `pdf::RenderLimits` (operators, glyphs, geometry, dashes, pixels, image decode
  and held bytes, clip depth), checks `RenderEnvironment::cancel`, culls what lies outside the
  clip and stops a page with a named limit; the JPEG decoder caps the work of a frame's scans.
  The editor keeps about 9 bytes per line, cuts rows at `kMaxRowBytes` and zero-width runs at
  `kMaxZeroWidthRun`, and rewraps from the edited row. A preview build is cancelled through
  `PdfOptions::cancel` when it is no longer wanted or passes 10 s. A new loop over input data
  spends a budget or proves its bound.
- Files the app reads or writes on its own (documents, exports, settings, Omarchy and PDF theme
  files, fonts.conf) go through `src/app/safefile.h`: `ReadRegularFile` (regular files only,
  never blocks on a FIFO, size-capped) and `WriteFileAtomically` (a random, exclusively created
  temporary file renamed over the destination; `WriteMode::Document` flushes, keeps the
  permission bits and writes through a symlink, `WriteMode::Output` replaces a symlink). Never a
  predictable `<path>.tmp` or `RayoMd::File::WriteAll` for them.
- Threads: the UI thread (platform event loop, UI, presenting); a tile pool of
  `clamp(hardware_concurrency - 1, 1, 4)` threads; one build worker for the engine; a preview
  pool of `clamp(hardware_concurrency / 2, 1, 3)` threads; one document loader that opens
  files. Workers hand results to the UI thread only through `Platform::PostToUi`. The UI
  thread does no file I/O and no O(document) work per keystroke beyond the one copy of the text
  a preview build takes (`mainwindow.h` states the preview policy); `bench.preview_latency`
  (ctest `rayomd-gui-bench-latency`) measures keystroke-to-preview latency.
- Nothing in startup or the UI thread waits for the font index's scan, which a cold font folder
  makes take up to a second. On Windows the interface font, the standard-font substitutes and
  the default fallbacks open from their known files, and the scan runs at background priority;
  `FontSet::Resolve` passes over a fallback that needs the index until it has scanned, and
  `FontIndex::OnScanned` makes the app shape and draw again. On Linux the interface font comes
  from the index before the first frame. Snapshot mode (`--snapshot`) prints where startup's
  time went.
- Reuse the engine's APIs instead of duplicating them: `TinyPdf::BuildPdf`,
  `TinyPdf::Internal::ParseTheme`, `RayoMd::PdfSource::Inspect`, `RayoMd::Inflate::ZlibReader`,
  `TinyPdf::Internal::UnfilterPngRow`, `TinyPdf::Internal::Cff`, `StandardTextWidth`,
  `RayoMd::Text::WinAnsiToUtf8` and `DecodeUtf8`, `RayoMd::Flate::ZlibCompress`,
  `RayoMd::File::ReadAll`.
- Generated `.inc` files are never edited by hand; change and rerun their script.

## Linux Rules

- libc only. `readelf -d rayomd-gui` lists `libc.so.6` and `ld-linux-x86-64.so.2` as NEEDED and
  nothing else; CI fails on any other entry. `ld-linux-x86-64.so.2` is glibc's program
  interpreter, which the kernel maps for every dynamic executable: it is NEEDED because the
  statically linked `libstdc++.a` objects with thread-local data (`eh_globals.o`, `mutex.o`)
  reference `__tls_get_addr`, and it opens no file. Add no library and no `dlopen` of our own.
  The one library loaded at run time is the engine's `dlopen` of `libm.so.6` when an SVG needs a
  transcendental function, inherited from `rayomd`.
- `--as-needed` cannot drop a library a discarded section referenced: libstdc++'s
  floating-point `std::from_chars` / `std::to_chars` reference `fesetround` and make
  `libm.so.6` NEEDED even after `--gc-sections`. Parse and format floating point with `strtod`
  and `snprintf` (the C locale; `setlocale` is never called).
- Every Wayland or D-Bus message added goes into the protocol tables (`wl_protocols.c`, the
  D-Bus calls in `portal.cpp`) with its signature from the protocol XML or interface
  definition. Every event that carries a file descriptor of a listed interface is listed, used
  or not: the wire skips unlisted events without taking fds off the queue.
- Nothing on the UI thread waits on another process: the D-Bus handshake, Hyprland's IPC and
  clipboard and drop transfers run on the event loop with deadlines. A D-Bus signal counts only
  from the sender it is about (the portal's current owner, the bus); clipboard transfers are
  capped in number, idle time and size (`data_transfer.h`).
- Keymap changes keep the xkb fixtures (`tests/data/xkb`, ctest `rayomd-gui-xkb`) passing; a
  keymap form the reader misses is added to the reader and to the fixtures, never handed to
  libxkbcommon.

## Hardening And Fuzzing

- The top-level `CMakeLists.txt` sets the exploit mitigations before
  `add_subdirectory(external/rayomd)`, so the engine compiled into the app gets them too. Linux
  release: `_FORTIFY_SOURCE=3`, `-fstack-protector-strong`, `-fstack-clash-protection`,
  `-fcf-protection` (C, C++ and the `.S` kernels, whose CET note `asm.h` emits), PIE (libraries
  compiled `-fPIE`), `-z relro -z now -z noexecstack`. MinGW release: `-fstack-protector-strong`,
  `_FORTIFY_SOURCE=2`, `--dynamicbase --nxcompat --high-entropy-va`. `_GLIBCXX_ASSERTIONS` is on
  for the app's own code in every configuration (`rgui_flags`); not for the engine, where it
  cost 7.5 % of `BuildPdf`.
- `tests/check_hardening.sh linux|windows <executable>` checks them (CI runs it on both): BIND_NOW,
  GNU_RELRO, a non-executable stack, PIE, `x86 feature: IBT, SHSTK` (one object built without
  `-fcf-protection`, an assembly file included, drops it for the whole binary), `__stack_chk_fail`
  and `__*_chk`, NEEDED; DllCharacteristics 0x0160 and no import of a delay-loaded DLL.
- A new reader of outside data gets a harness in `tests/fuzz/` (listed in `harness.h`,
  `tests/fuzz.cmake`, `tests/fuzz/CMakeLists.txt`, `run_fuzzers.sh` and `fuzz.regressions`) and
  seeds in `make_seeds.cpp`. A crash a fuzzer finds is fixed with its minimized input committed
  under `tests/fuzz/regressions/<harness>/`.
- CodeQL (`codeql.yml`, security-extended) fails on any result in the app's code. A result that
  is no flaw is fixed in the code where possible; otherwise its rule and file go into
  `.github/codeql/reviewed.json` with the reason, never a blanket query exclusion.

## Build And Test

Linux (Arch, as CI):

```sh
cmake --preset linux-release && cmake --build --preset linux-release && ctest --preset linux-release
```

Windows (MSYS2 UCRT64), or a MinGW-w64 cross-build from Linux:

```sh
cmake --preset windows-mingw && cmake --build --preset windows-mingw
cmake -S . -B build/mingw -DCMAKE_SYSTEM_NAME=Windows -DCMAKE_C_COMPILER=x86_64-w64-mingw32-gcc \
  -DCMAKE_CXX_COMPILER=x86_64-w64-mingw32-g++ -DCMAKE_RC_COMPILER=x86_64-w64-mingw32-windres \
  -DCMAKE_BUILD_TYPE=Release
```

`build/linux-release/tests/rayomd-gui-tests gfx.` runs the tests whose names begin with
`gfx.`. Tests that need an outside tool (poppler's `pdftocairo`, `djpeg`, `xkbcli`,
`dbus-run-session`, `weston`, `sway`) are separate ctest entries, added when CMake finds the
tool.

Releases (`release.yml`): every push to `main` replaces the `continuous` pre-release with the
Linux tarball, the Arch package (`linux/pkgbuild`, its `pkgver` set from `VERSION`) and the
Windows zip; a tag `v<VERSION>` publishes that version's release. The Linux binary is built on
ubuntu-22.04 so it runs on glibc 2.34 and newer: keep the code building with GCC 11 and
CMake 3.22, including every header a file uses (newer libstdc++ pulls in more by itself).

Fuzzing (Clang with compiler-rt; CI runs every harness 60 s):

```sh
cmake --preset linux-fuzz && cmake --build --preset linux-fuzz
tests/fuzz/run_fuzzers.sh build/linux-fuzz 600 build/fuzz-work [harness...]
build/linux-fuzz/tests/fuzz/rgui-fuzz-pdf <crash file>   # reproduce one input
```
